# 软件架构

PlantHub 在 ESP32 上运行轻量分层模块化单体。可信家庭局域网内的浏览器通过本地 HTTP API 操作设备。网络重连独立处理，必要功能在互联网中断时继续运行，时间失效处理见 [产品规范](PRODUCT_SPEC.md#时间与历史)。

## 分层与依赖

| 层 | 职责与依赖 |
| --- | --- |
| Core | 业务模型、参数校验、标定与换算、灌溉规则和状态机。仅依赖标准 C++ 与本层代码，可在 Windows、Linux、macOS 独立构建。禁止依赖 Arduino、硬件、实际时钟、存储、HTTP 和 JSON。 |
| Application | 组织监测、灌溉、调度、配置、历史和系统用例。依赖 Core 和自身接口。按实际替换或测试需求定义传感器、水泵、时钟、配置和历史接口。 |
| Platform | 实现 Application 所需的平台接口，负责板级配置、驱动、存储、Wi-Fi、时钟和诊断。依赖应用接口、所需 Core 类型与嵌入式框架。 |
| Web | 处理 HTTP 路由、参数解析、访问控制、JSON 及静态资源响应。依赖 Application 和必要的 Core 类型。禁止直接访问 GPIO 或绕过灌溉入口。 |
| Bootstrap | `main.cpp` 创建对象、注入依赖、初始化及启动服务。业务规则由相应分层管理。 |

依赖保持单向，普通计算、数据模型、校验和状态机直接使用函数、结构体或具体类。前端位于 `frontend/`，业务访问统一走 HTTP API。M0-B 创建实际使用的入口、板级配置与测试，其他模块随用例落地。

Core 以调用方提供的可用逻辑通道校验业务配置。后续设备适配由板级配置提供已启用通道的映射，由驱动判定 ADC 量程和采集状态。配置校验返回业务错误及相关实体。灌溉模块在静态就绪检查之上验证请求来源及运行条件。业务关系和就绪条件见 [产品规范](PRODUCT_SPEC.md#模型与关系)。

## 灌溉执行

手动、定时和智能请求共用 Application 入口，依次检查条件、持久化预留额度及执行凭据、启动、停止和保存结果。Core 提供条件判断及状态转换。产品约束详见 [灌溉规则](PRODUCT_SPEC.md#灌溉规则)。

- `core/model` 保存静态配置和普通记录类型，`core/validation` 校验配置与静态就绪条件，`core/calibration` 换算时长、水量与结算额度。M1-B 的 `core/irrigation` 管理统一许可、全局执行资源、日期与自动触发，以及关键状态候选与恢复。
- 一个 Core 实例维护全局执行状态。受理后生成计划快照，可靠保存预留及执行 ID 后才发出一次启动许可。许可携带计划与最大绝对单调截止时间。执行中的快照固定流量、剂量和时限。设备确认关泵后生成结算候选，可靠结算后释放资源并可提取对应的历史记录。
- 关键状态包含额度日期及固定偏移、定时消费水位与当日定时保护、分区累计及通道绑定、唯一待结算计划、执行 ID 水位、有限手动请求凭据、自动暂停、故障锁定及发生过灌溉的分区和通道。单调时间基准、最新读数和低湿度累计、候选任务、分组游标及设备事件均在当前启动周期内维护。
- M1-C 顺序驱动 Core，刷新时间及读数，确保每次只有一个关键状态快照在写入，按保存 ID 确认可靠结果并处理失败。它负责保护配置变更中的 ID、分区与供水通道身份及冷却关联，变更相关规则时重置自动判断，组织候选冲突及分组推进，确定手动请求凭据的有效保留期，并按执行 ID 写入普通历史。设备适配须使发出的启动许可与优先停止之间具有可靠的撤销语义，并报告可信的启停事实。

后续 FreeRTOS 设备控制任务负责启停、互斥、最长运行时间、独立停止时限及执行状态。Web、网络、采集、规则调度和文件读写留在普通服务。两侧通过有限容量命令队列与状态快照通信，停止使用独立优先路径。网页阻塞、历史下载和网络重连期间仍须能停止设备。

## 存储与发布

NVS / Preferences 保存配置、标定、网络凭据和关键运行状态。配置含 `schemaVersion`，完整校验和持久化成功后才切换生效。关键状态缺失、损坏或不兼容时，须提示故障并禁止正常灌溉。首次初始化需由应用确认。LittleFS 保存用户监测历史及灌溉记录，RAM 保留实时读数、状态与短期缓存。

后续构建阶段将 HTML、CSS、JS、图标和本地图表库打包、压缩并嵌入固件。网页与固件一起发布，历史数据保存在独立的文件系统分区。Flash 布局见 [Rev B 硬件基线](../hardware/rev-b/README.md#flash-布局)。

## REST API 规划

接口使用 `/api/v1/`，API 版本独立于固件版本。HTTP 和 JSON 转换由 Web 层处理。业务及访问约束见[产品规范](PRODUCT_SPEC.md)。当前最小固件用于构建验证。

| 方法 | 路径（相对 `/api/v1`） | 用途 |
| --- | --- | --- |
| GET | `/status` | 设备状态 |
| GET | `/monitoring/latest` | 最新环境及土壤监测 |
| GET、POST | `/plants` | 列表、新增 |
| PUT、DELETE | `/plants/{id}` | 编辑、删除 |
| GET、PUT | `/sensors/{id}` | 查询探头与修改标定配置 |
| GET、PUT | `/pumps/{id}` | 查询水泵与修改标定配置 |
| GET、POST | `/zones` | 列表、新增分区 |
| GET、POST | `/groups` | 列表、新增分组 |
| GET、PUT | `/zones/{id}/rule` | 查询、更新分区规则 |
| POST | `/irrigation/requests` | 受理灌溉请求 |
| POST | `/irrigation/stop` | 优先停止灌溉 |
| GET | `/irrigation/status` | 查询执行状态 |
| GET | `/history/readings` | 查询监测历史 |
| GET | `/history/irrigation` | 查询灌溉记录 |
| GET | `/history/export` | 导出 CSV |
| GET、PUT | `/settings` | 查询、更新配置 |
| GET | `/diagnostics` | 设备诊断 |

- 实现时统一 JSON 字段风格、稳定实体 ID、单位、机器可读错误码和 HTTP 状态码。限制请求体、历史查询范围和分页，按[存储约定](#存储与发布)验证并保存配置。
- 手动灌溉使用唯一请求 ID，重复点击或网络重试须去重。HTTP `202` 表示已受理。执行状态表达受理、执行中、正常结束、人工停止、失败及结果未知。
- 配置和控制接口遵循[访问规范](PRODUCT_SPEC.md#访问与首版范围)。业务 API 禁止返回真实 Wi-Fi 密码，并仅开放用户业务配置。物理引脚和设备地址由 `BoardProfile` 管理。

## 已确认的架构决策

| 编号 | 决策 | 原因及约束 |
| --- | --- | --- |
| ADR-001 | ESP32 独立运行、本地优先、模块化单体 | 减少家庭部署依赖，断网时保留必要的设备功能。 |
| ADR-002 | PlatformIO、pioarduino、Arduino-ESP32 3.3.x 与 C++17 | 兼顾开发效率、S3 支持和复现性，使用固定构建版本。 |
| ADR-003 | 原生 HTML/CSS/JS、ES Modules 和本地图表库 | 减少设备资源及部署依赖。Chart.js 4.x 随对应功能引入。 |
| ADR-004 | Arduino WebServer 与 REST API | 浏览器直连设备，JSON 转换留在 Web 层，使用 ArduinoJson 7.x。 |
| ADR-005 | Core、Application、Platform、Web 四层 | 将业务、设备适配和传输职责分开，入口负责组装。 |
| ADR-006 | Core 使用标准 C++，支持 Native 测试 | 在没有开发板和 Arduino 运行时的环境验证核心规则。 |
| ADR-007 | 按需抽象硬件、时钟和存储 | 接口服务实际替换和测试需求。 |
| ADR-008 | 引入 `IrrigationZone` | 分区作为最小灌水执行单元，支持共享水泵和分组。 |
| ADR-009 | 构建板卡、物理硬件及用户配置独立 | 业务配置变更不得重定义电气连接。 |
| ADR-010 | 保持轻量工程 | 家庭设备采用直接的函数、类和必要接口，规避微服务、ORM、完整 DDD、通用 Repository 和 CRUD 框架、依赖注入容器、事件总线及复杂插件体系。 |
| ADR-011 | 三种灌溉模式统一入口 | 三种请求共同受安全约束及执行记录管理。 |
| ADR-012 | 独立水泵控制任务 | 避免普通服务的阻塞影响启停时限。 |
| ADR-013 | 低湿度触发、固定剂量、冷却后判断 | 为水分渗透保留时间，控制单轮灌水量。 |
| ADR-014 | 限制单次和每日额度，持久化凭据 | 在重启、回拨及执行量不确定时保守记账。 |
| ADR-015 | 上电停泵、互斥、人工停止及重启不续灌 | 默认保守运行，实物上电、复位及掉电的行为须验收。 |
| ADR-016 | 单调时间与日期时间独立 | 避免校时跳变影响运行时限。 |
| ADR-017 | NVS 保存配置和关键状态 | 正常灌溉以关键状态可靠持久化为前提。 |
| ADR-018 | LittleFS 保存历史、网页资源内嵌 | 网页更新与历史数据隔离。 |
| ADR-019 | 16 MiB Flash 预留双约 4 MiB APP 分区 | 为后续 OTA 留出空间，容量及类型由实物确认。 |
| ADR-020 | 默认 60 秒采集、5 分钟存储及 14 天监测历史 | 以较低写入频率支持日常观察。 |
| ADR-021 | 按日追加 CSV、配置含 schema 版本 | 支持历史清理、导出与配置兼容性判断。 |
| ADR-022 | 首版五页、两盆植物使用闭环 | 先验证标定、监测、灌溉和回看，容量按现有通道限制。 |
| ADR-023 | 单管理员及可信局域网访问 | 配置及控制接口认证，局域网 HTTP 端口禁止映射公网。 |
| ADR-024 | 远程、AI、OTA 和未安装传感器功能延期 | 功能随真实需求与硬件验证逐步引入。 |
| ADR-025 | 单仓库、短期分支、语义化版本和 AGENTS.md | Git 维护可追溯的阶段变更。 |
| ADR-026 | 执行 [M0～M7 路线](ROADMAP.md) | 按阶段验证工程、业务和实物。 |
| ADR-027 | `v0.1.0` 为有人值守原型 | 长期无人值守需要单独的硬件防护和稳定性验收。 |
